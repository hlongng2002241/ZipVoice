# Multilingual (EN/VI/ZH) Text Front-End for ZipVoice

- **Date:** 2026-08-28
- **Author:** LongNH (with Claude Code assistance)
- **Status:** In Progress — Sprints 001-002 done for everything achievable
  without paired audio-text training (see each sprint's Progress section);
  Sprint 003's tokenizer decision is **final: Qwen2.5-0.5B** (not mBERT — see
  [../../adr/2026-08-28__choose_qwen25_tokenizer.md](../../adr/2026-08-28__choose_qwen25_tokenizer.md)),
  decided from real corpora at 690M-character scale across all three
  languages; embedding form and duration-scheme ablations remain pending;
  Sprint 004 (full training run) not started, blocked on paired audio-text
  training infrastructure

## Goal

Replace ZipVoice's phonemizer-based, EN/ZH-oriented text front end with an
existing pretrained multilingual tokenizer plus `[LANG:xx]` special tokens,
select the specific tokenizer/embedding configuration via an empirical bakeoff
(not compression-ratio guesswork), and land a frozen checkpoint that correctly
handles mixed EN/VI/ZH text — including code-switched sentences the current
Unicode-range segmentation cannot handle.

## Background

See [../../proposals/2026-08-28__mbert_multilingual_tokenizer.md](../../proposals/2026-08-28__mbert_multilingual_tokenizer.md)
and [../../proposals/2026-08-28__primary_language_conditioning.md](../../proposals/2026-08-28__primary_language_conditioning.md),
and the decisions recorded in
[../../adr/2026-08-28__adopt_pretrained_multilingual_tokenizer.md](../../adr/2026-08-28__adopt_pretrained_multilingual_tokenizer.md)
and [../../adr/2026-08-28__language_hint_as_special_tokens.md](../../adr/2026-08-28__language_hint_as_special_tokens.md).

Both proposals and their Codex (gpt-5.6-sol, high reasoning effort) review
converged on: reuse an existing pretrained tokenizer rather than train a custom
one; add `[LANG:xx]` as reserved special tokens rather than a separate
conditioning pathway; and replace the original tokens-per-character-only
selection metric with a proper bakeoff measuring actual pronunciation/WER
outcomes. This plan is also the hard dependency for
[../2026-08-28__flowtts_grpo_rl/2026-08-28__overview.md](../2026-08-28__flowtts_grpo_rl/2026-08-28__overview.md) —
per [../../adr/2026-08-28__sequence_rl_after_frontend_freeze.md](../../adr/2026-08-28__sequence_rl_after_frontend_freeze.md),
RL post-training must not start until this plan's final checkpoint is frozen.

## Scope

- **In scope:** held-out multilingual evaluation sets and data-label contracts;
  `[LANG:xx]` vocabulary + zero-duration handling; the tokenizer/embedding
  bakeoff (mBERT, Qwen2.5-0.5B, corrected-phonemizer baseline, character-level
  baseline, pretrained-vs-scratch embedding, uniform-vs-weighted duration); the
  final supervised training run with the chosen configuration frozen.
- **Out of scope:** FlowTTS-GRPO RL post-training (separate plan, gated on this
  one's completion); building a fully custom tokenizer from scratch (ruled out
  by ADR); production/serving rollout mechanics beyond producing a versioned
  checkpoint.

## Approach

1. [Sprint 001 — Evaluation sets & data contracts](2026-08-28__sprint_001__eval_and_data_contracts.md):
   build the fixed EN/VI/ZH/code-switched eval sets and define "primary
   language" precisely, before any bakeoff or training happens.
2. [Sprint 002 — `[LANG:xx]` special tokens & duration handling](2026-08-28__sprint_002__special_tokens_and_duration.md):
   land the vocabulary reservation mechanism, zero-duration exclusion for
   control tokens, dynamic label dropout, and a probe confirming a prefix tag
   actually influences the model's output.
3. [Sprint 003 — Tokenizer + embedding bakeoff](2026-08-28__sprint_003__tokenizer_embedding_bakeoff.md):
   run Codex's revised selection methodology (per-language/code-switch WER,
   pronunciation spot checks, normalization coverage, latency/memory) across
   candidates and embedding-init strategies; pick the configuration to freeze.
4. [Sprint 004 — Frozen front-end training run](2026-08-28__sprint_004__frozen_frontend_training_run.md):
   full training run with the winning configuration, regression-tested against
   current EN/ZH quality and validated on Vietnamese, producing the checkpoint
   the RL plan depends on.

## Risks & Open Questions

| Risk / Question | Impact | Mitigation / Owner |
| --- | --- | --- |
| "Primary language" undefined for code-switched utterances; corpus language labels may be noisy | Bad training labels for `[LANG:xx]` and bakeoff evaluation | Sprint 001 defines the label precisely and audits existing corpus metadata before anything downstream uses it |
| Tokens-per-character was the only tokenizer-selection metric in the original draft | Could pick a tokenizer that compresses well but pronounces badly | Sprint 003 replaces it with per-language/code-switch WER and pronunciation spot checks |
| Dropping phonemizer removes implicit text normalization (numbers, dates, abbreviations) along with G2P | Silent regression on previously-handled text patterns | Sprint 003's bakeoff explicitly includes a normalization-coverage check per candidate |
| `[LANG:xx]` prefix token's influence on the full sequence is assumed, not proven | Feature could be a no-op | Sprint 002 includes an explicit probe (compare outputs across tags on identical text) as a gate before proceeding |
| Small-scale bakeoff runs may not predict full-scale training behavior | Wrong tokenizer choice discovered only after the full run | Sprint 004's regression suite is the final gate; a failure there loops back to sprint 003, not straight to shipping |

## Testing & Validation

Per-language and code-switch WER/CER against sprint 001's held-out sets;
pronunciation spot checks on ambiguous Latin-script words and homographs; a
regression suite confirming no quality loss on existing EN/ZH behavior; the
user's existing Vietnamese reward/eval models for VI-specific validation.

## Rollout

The phonemizer-based `EmiliaTokenizer` path remains available as a fallback
during this work — nothing is deleted until the new front end passes sprint
004's regression gate. Once frozen, the resulting checkpoint is versioned and
becomes the input the RL plan (`2026-08-28__flowtts_grpo_rl`) consumes; no
further front-end changes should land against that checkpoint without
re-opening the RL plan's dependency per ADR.
